The Mental Model

Know Cold

EPICS is a toolkit for building distributed control systems. It solves the same problem as Tango: making hardware on a beamline — motors, detectors, valves, power supplies — addressable by software running anywhere on the network. The fundamental data abstraction is the Process Variable (PV). Everything in EPICS is a named PV. You read it, write it, or subscribe to changes on it. That is the entire client-facing API.

The PV lives inside an IOC (Input/Output Controller). The IOC is a software process — running on a VME crate, an embedded Linux box, or a regular server — that owns a set of PVs and knows how to talk to the underlying hardware. Clients connect to IOCs using the Channel Access (CA) protocol, which is UDP for discovery and TCP for data. A newer protocol, PV Access (PVA), extends this with structured data types needed for detector images and complex scientific data.

One sentence summary to say out loud: "EPICS is a publish-subscribe control system where hardware state is exposed as named Process Variables served by IOCs over Channel Access, and any network client can read, write, or monitor those variables in real time."

Tango Parallel

The EPICS IOC ≈ Tango DeviceServer. The Process Variable ≈ Tango Attribute. Channel Access ≈ the ZMQ/CORBA transport layer. EPICS_CA_ADDR_LIST ≈ TANGO_HOST — both are the mechanism for clients to find servers. The biggest conceptual difference: Tango organizes state into Devices with attributes and commands; EPICS is flatter — everything is a PV, and "devices" are just naming conventions for groups of PVs.

01

The IOC

Know Cold

The IOC is the server in EPICS. It runs a real-time database of records (each record is a PV), handles hardware I/O through device support modules, and serves PV values to clients over CA. Two flavors exist: a hard IOC runs on dedicated hardware (VME crates, embedded systems), and a soft IOC runs on any Linux server without physical I/O — often used for simulations, software-only PVs, or testing. At LCLS both are in use.

An IOC is defined by two artifacts: the startup script (st.cmd) and the database files (.db). The startup script boots the IOC shell, loads device drivers, and loads the record database. The database files define the PVs — their names, types, scan rates, alarm thresholds, and hardware addresses.

Startup Script Anatomy — st.cmd

Tango Parallel

The .db record database ≈ a Tango device class definition. Records are the attributes. SCAN field ≈ Tango polling interval. INP/OUT link ≈ Tango device property pointing to hardware address. DESC, EGU, PREC ≈ Tango attribute configuration (unit, format, label). The alarm fields (HIGH, HIHI, HSV) are EPICS's built-in equivalent of Tango's alarm/warning thresholds.

02

Process Variables

Know Cold

A Process Variable is a named value served by an IOC. The name is a plain string up to 61 characters. At SLAC the convention is SYSTEM:DEVICE_TYPE:LOCATION:SIGNAL — for example LCLS:GAS:HUTCH1:PRES1 or LCLS:LASER:PUMP:PWR. The colon is a naming separator by convention, not a protocol requirement.

Every PV has fields that are accessed by appending a dot and the field name. The bare PV name refers to the VAL field, which is the primary data value. Common fields you will encounter:

ShellPV field access — the VAL field is the default
# bare name = VAL field = the primary value caget LCLS:GAS:PRES1 # → 8.73e-07 # explicit field access caget LCLS:GAS:PRES1.EGU # → torr (engineering units) caget LCLS:GAS:PRES1.DESC # → Gas system pressure ch1 caget LCLS:GAS:PRES1.SEVR # → NO_ALARM / MINOR / MAJOR / INVALID caget LCLS:GAS:PRES1.STAT # → alarm status (HIGH, HIHI, LINK, etc.) caget LCLS:GAS:PRES1.TIME # → last update timestamp caget LCLS:GAS:PRES1.SCAN # → 1 second (scan rate) caget LCLS:GAS:PRES1.HIHI # → 1e-5 (MAJOR alarm threshold) caget LCLS:GAS:PRES1.PREC # → 2 (decimal precision)
Key Field: SCAN

The SCAN field controls how the IOC refreshes the PV. Passive means only on an external trigger (a CA put, or another record driving it). Periodic values like "1 second", "0.1 second", "10 second" are polling periods. I/O Intr means the driver interrupts when the hardware has new data — used for event-driven hardware like beam timing.

Tango Parallel

Tango attribute types map directly: DEV_DOUBLE ≈ ai/ao, DEV_BOOLEAN ≈ bi/bo, DEV_ENUM ≈ mbbi/mbbo, DEV_FLOAT_SPECTRUM ≈ waveform with FTVL=FLOAT, DEV_STRING ≈ stringin/stringout. Tango Commands have no direct record equivalent — they are implemented in EPICS as a combination of a bo or mbbo PV (the command trigger) plus a seq record (the sequenced action).

04

Channel Access Protocol

Know Cold

Channel Access (CA) is the original EPICS network protocol. It uses UDP port 5064 for PV name searches and TCP port 5064 for all data exchange once a channel is opened. When a client asks for a PV, it broadcasts a UDP search packet; the IOC serving that PV replies with its IP and port; the client opens a TCP connection and the channel is established.

The CA Repeater is a helper process running on the client host at UDP port 5065. It receives IOC beacon packets — periodic UDP heartbeats that IOCs broadcast every ~15 seconds — and relays them to all CA clients on the local machine. If the beacon stops and then resumes, the client library detects a beacon anomaly, which signals that the IOC restarted and any outstanding channel connections need to be re-verified.

Name resolution is controlled by EPICS_CA_ADDR_LIST, an environment variable containing space-separated IP addresses or subnet broadcast addresses. If unset, CA broadcasts to the local subnet. On a multi-subnet facility like LCLS, it must be explicitly configured to reach IOCs on different segments.

ShellEssential environment variables
# Tell CA where to search for IOCs on multiple subnets export EPICS_CA_ADDR_LIST="10.0.1.255 10.0.2.255 172.27.100.10" export EPICS_CA_AUTO_ADDR_LIST="NO" # disable default local broadcast # Timeout for initial PV connection (seconds) export EPICS_CA_CONN_TMO="30.0" # Maximum array size in bytes (default 16384 = ~4K floats) # Raise this to handle large detector waveforms export EPICS_CA_MAX_ARRAY_BYTES="10000000"
Tango Parallel

EPICS_CA_ADDR_LIST ≈ TANGO_HOST. Both tell clients where to find servers. The difference: TANGO_HOST points to a central database server (MySQL-backed) that knows all device locations. CA name resolution is peer-to-peer UDP search — no central registry. This makes EPICS more resilient (no database single point of failure) but means new clients must know the subnet addresses to search.

Interview Trap

If asked "what is the CA Repeater?" — it is not the IOC, not the CA gateway, and not a proxy. It is a client-side daemon on port 5065 that forwards IOC beacon packets to local CA clients so they can detect IOC restarts. One CA Repeater per machine, started automatically by the first CA client process on that host.

05

PV Access (PVA)

LCLS-II

PV Access is the newer EPICS protocol, part of EPICS 7. It uses port 5075 and carries structured data types (pvData structures) rather than the flat scalar/array types of CA. The key advantage is that a single PV can contain a complex object — for example, a detector image plus its metadata, timestamps, and attributes all in one atomic request.

The standard EPICS normative types (NT types) you will encounter at LCLS:

NT TypeWhat it carriesWhere you see it
NTScalarSingle value with alarm, timestamp, descriptorScalar PVs on EPICS 7 IOCs
NTScalarArrayArray with alarm, timestampWaveforms from EPICS 7 IOCs
NTNDArrayN-dimensional detector image + attributes + timestampsareaDetector cameras, LCLS detector systems
NTTableColumnar data structureScan data, tabular instrument data
ShellPVA command-line tools — different binaries from CA tools
# PVA get — prefix pva:// optional but explicit pvget LCLS:DET1:IMAGE pvget -r "field(value,alarm,timeStamp)" LCLS:DET1:IMAGE # PVA monitor pvmonitor LCLS:DET1:IMAGE # CA put still works for scalar PVs via caput # PVA put pvput LCLS:GAS:VALVE1:CMD 1
Tango Parallel

NTNDArray ≈ Tango DevImage attribute + Tango Pipe for metadata. The concept of carrying structured, typed, self-describing data is the same problem Tango Pipes were invented to solve. PVA is EPICS's answer to the same gap. EPICS 7 is the version that unifies CA and PVA in one IOC — analogous to how Tango 9+ unified the event system.

SLAC / LCLS

LCLS-I runs primarily on EPICS 3 (CA only). LCLS-II (the superconducting upgrade) runs EPICS 7, which carries both CA and PVA in the same IOC. areaDetector — the framework for detector systems at LCLS — uses PVA NTNDArray for image data. If asked about LCLS-II at SLAC, the transition from CA to EPICS 7 with PVA is a meaningful answer.

Python Interfaces

Know Cold

Three Python libraries cover 95% of EPICS Python work. Know the difference between them so you can name the right one when asked.

pyepics — the standard workhorse

Wraps libca (the C CA client library). Callback-based. Thread-safe with care. Most legacy LCLS Python control code uses pyepics.

Python · pyepicsRead, write, and monitor
import epics # Synchronous read/write — blocks until response val = epics.caget('LCLS:GAS:PRES1') epics.caput('LCLS:GAS:VALVE1:CMD', 1) # Read with metadata data = epics.caget('LCLS:GAS:PRES1', with_ctrlvars=True) # data['units'], data['severity'], data['upper_alarm_limit'] etc. # Monitor: callback fires on every value change def on_pressure_change(pvname, value, timestamp, **kw): if value > 1e-6: handle_alarm(pvname, value) epics.camonitor('LCLS:GAS:PRES1', callback=on_pressure_change) # PV object — better for long-lived references pv = epics.PV('LCLS:GAS:PRES1') pv.add_callback(on_pressure_change) print(pv.value, pv.units, pv.severity)

caproto — pure Python, asyncio-native

No C library dependency. Implements CA protocol in pure Python. Asyncio-native, making it the right choice for high-throughput monitoring or when you need to run many PV subscriptions concurrently without callbacks.

Python · caprotoSync and async interfaces
# Sync client — simplest for one-shot reads from caproto.sync.client import read, write, monitor response = read('LCLS:GAS:PRES1') print(response.data[0]) # the value # Async client — for concurrent monitoring without threads import asyncio from caproto.asyncio.client import Context async def monitor_pressure(): ctx = await Context.create() chan, = await ctx.get_many_pvs('LCLS:GAS:PRES1') await chan.subscribe(data_type='time') async for event in chan.updates(): print(event.data[0], event.metadata.timestamp)

p4p — PV Access client and server

The standard Python interface for PVA. Required for NTNDArray detector data, NTTable, and any EPICS 7 structured PV.

Python · p4pPV Access — structured data
from p4p.client.thread import Context ctx = Context('pva') # Get a PVA channel — returns a Value (pvData structure) val = ctx.get('LCLS:DET1:IMAGE') print(val.value) # the image array print(val.timeStamp.secondsPastEpoch) # Subscribe def on_image(value): process_frame(value.value, value.attribute) sub = ctx.monitor('LCLS:DET1:IMAGE', on_image)
SLAC / LCLS Python Stack

LCLS Python control code typically uses pyepics for CA channels (motors, diagnostics, interlocks) and p4p for detector data arriving as NTNDArray. The higher-level abstraction layer you may hear about at SLAC is ophyd (developed at BNL, used at some SLAC beamlines) — it wraps pyepics PVs into "Device" objects with Signal components, similar to how a Tango DeviceProxy aggregates attributes. A newer SLAC-specific layer is pcdsdevices, which builds ophyd devices for LCLS hardware.

PyDM & the SLAC GUI Stack

SLAC-built

PyDM (Python Display Manager) is a PyQt5/6-based framework built at SLAC for building EPICS control room displays. It replaces older tools like MEDM (Motif-based, 1990s-era) and partially replaces CS-Studio (Java-based). You can mention PyDM by name in the interview — it signals you researched SLAC's actual toolchain, not just EPICS generics.

PyDM's architecture: every GUI widget is a data plugin consumer. Widgets like PyDMLabel, PyDMByteIndicator, and PyDMWaveformPlot connect to channels via a URI scheme. The CA data plugin handles ca://PV_NAME, the PVA plugin handles pva://PV_NAME. Displays are defined either as .ui files (Qt Designer) or as .py files (pure Python). Macros (${DEVICE}) substitute into channel addresses at runtime, making a single display reusable across multiple device instances.

Python · PyDM displayA minimal programmatic display — .py format
from pydm import Display from pydm.widgets import PyDMLabel, PyDMByteIndicator, PyDMWaveformPlot from qtpy.QtWidgets import QVBoxLayout class GasSystemDisplay(Display): def __init__(self, parent=None, args=None, macros=None): super().__init__(parent, args, macros) layout = QVBoxLayout() # ${DEVICE} is substituted from macros at runtime pressure_lbl = PyDMLabel( channel="ca://${DEVICE}:PRES1" ) valve_ind = PyDMByteIndicator( channel="ca://${DEVICE}:VALVE1:CMD" ) layout.addWidget(pressure_lbl) layout.addWidget(valve_ind) self.setLayout(layout) def ui_filename(self): return None # pure-Python display, no .ui file
ShellLaunching a PyDM display with macros
# Launch a .py display with macro substitution pydm --macros "DEVICE=LCLS:GAS,HUTCH=HXR" gas_system.py # Launch a .ui file (Qt Designer output) pydm --macros "DEVICE=LCLS:GAS" gas_system.ui

Diagnostic Toolkit

Know Cold

These are the first tools you reach for when something breaks. Know them by name and know what each one tells you.

camonitor PV_NAME
Subscribes to a PV and prints every value change with timestamp. The single most-used EPICS diagnostic command. Leave it running while you debug — if the line stops updating, the PV is frozen. If it never appears, the PV is disconnected. Shows timestamp, value, and alarm severity on each line.
cainfo PV_NAME
Fetches metadata about a PV without reading its value: which IOC serves it, its CA server hostname and port, its data type, element count, access rights, and alarm thresholds. If it returns "Channel not found," the PV is either nonexistent or unreachable — check EPICS_CA_ADDR_LIST.
caget PV_NAME    caget -a PV_NAME
Single read. With -a flag, returns all control-layer metadata (units, limits, alarm thresholds, precision, status). Use -a when diagnosing alarm states — it shows HIHI/HIGH/LOW/LOLO limits in one command.
caput PV_NAME value    caput -c PV_NAME value
Write a value. With -c (callback) flag, waits for the IOC to process the put and confirm completion — important when writing to a record that drives hardware and you need to know the write succeeded before proceeding.
pvget PV_NAME    pvmonitor PV_NAME
PV Access equivalents of caget and camonitor. Use these when the PV is on an EPICS 7 IOC or when you need structured data (NTNDArray, NTTable). If pvget succeeds but caget fails, the channel is PVA-only.
caRepeater    caproxy
caRepeater is normally started automatically — run it manually only if you suspect it died (symptoms: beacon anomaly not detected, IOC restart not noticed by clients). caproxy is a CA gateway proxy, used when clients and IOCs are on different network segments and broadcast cannot reach across.

IOC Shell Commands (inside a running IOC)

EPICS IOC ShellCommands you run in the soft IOC terminal for diagnostics
# Show all threads and their status epicsThreadShowAll # Show callback statistics — reveals callback queue pressure callbackStats # Show all records and their current values dbl # list all record names dbpr LCLS:GAS:PRES1 # print one record's complete field table # Force a record to process immediately dbpf LCLS:GAS:PRES1.PROC 1 # Check asyn driver status asynReport 4 "GAS_PORT"

Common Failure Modes

Know Cold

The five scenarios that come up in every controls engineer's first month. Know the symptom → diagnosis → fix sequence for each.

1. Soft IOC running but PVs unresponsive
Symptom: camonitor shows no updates. cainfo shows channel found but value stale. IOC process is alive (ps confirms).
Likely cause: A synchronous operation in a CA callback thread is blocking the entire IOC callback system. EPICS callback threads must never block — if device support or a user callback performs a blocking I/O or sleeps, all callbacks queue behind it. Diagnosis: Run epicsThreadShowAll and callbackStats in the IOC shell. Look for a thread stuck in a long-running state. Check for callback queue depth > 0. Fix: Move blocking work to a separate worker thread; callbacks must execute in microseconds and return.
2. Channel not found — PV unreachable from client
Symptom: cainfo returns "Channel not found". camonitor never connects. IOC is running on another host.
Likely cause: Client's CA address list doesn't reach the IOC's subnet. Diagnosis: Run echo $EPICS_CA_ADDR_LIST — if empty or wrong, this is the cause. Alternatively the IOC is on a subnet blocked by a firewall. Fix: Add the IOC's subnet broadcast address or the IOC's direct IP to EPICS_CA_ADDR_LIST. If cross-subnet: deploy a caproxy gateway on a host visible to both sides.
3. Beacon anomaly — IOC restarted unexpectedly
Symptom: camonitor shows momentary disconnect then reconnect. IOC log shows a fresh start. Timestamp on PVs jumps.
Cause: The IOC process crashed and was restarted (by procServ, systemd, or manually). Clients detect the restart because the beacon sequence number resets. Diagnosis: Check the IOC log file for the crash reason — look for segfault, OOM kill, or exception. Check dmesg for OOM killer events. Fix: Address the root cause. Use procServ to auto-restart IOCs in production (standard at LCLS) so the outage window is seconds.
4. PV value frozen / not scanning
Symptom: caget returns a value but camonitor never sees updates. cainfo shows last update time is old.
Likely causes: (a) SCAN field set to Passive with no driver to trigger it — check caget PVNAME.SCAN. (b) The asyn driver is in an error state and not calling the record back — run asynReport 4 "PORT_NAME" in the IOC shell to inspect driver status. (c) Record DISA field is set (disabled). Fix for (a): Change SCAN to a periodic value, or add a fanout record to trigger it.
5. CA client causing IOC CPU spikes
Symptom: IOC host CPU climbs under load. Many clients monitoring fast-scanning PVs. Some PVs scan at 10 Hz or faster.
Cause: Each CA monitor subscription generates network traffic and IOC processing on every scan period. With many monitors on fast PVs, this compounds. Diagnosis: Run camonitor -c PVNAME.SCAN to check the actual scan rate; check how many clients have subscriptions using cainfo PVNAME (shows connection count). Fix: Use MDEL (Monitor Deadband) and ADEL (Archive Deadband) fields on ai records to suppress CA events when the value hasn't changed meaningfully. Consider reducing SCAN on diagnostic PVs to "5 second" outside of active experiments.

Tango → EPICS Translation Map

Your Advantage

Your native system is Tango. EPICS is the same class of problem with different vocabulary. This table is your mental translation layer — you don't need to pretend you don't know Tango; you can use this mapping in the interview to show architectural depth in both systems.

When asked about EPICS depth, you don't need to hide the Tango background — you can lean into it: "My native controls system is Tango, which is architecturally comparable to EPICS — both use a device-server model with published attributes and a publish-subscribe event system. That answer is honest, specific, and demonstrates architectural breadth. It is more credible than claiming EPICS-native experience you don't have, and far stronger than fumbling a generic answer.
