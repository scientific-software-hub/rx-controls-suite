Guarded Tomography Scan, Orchestrated by Prefect

A walkthrough of what actually happened when this ran against the live docker stack — with the Prefect UI screens it produced, annotated, plus the two real bugs that surfaced along the way and how they got root-caused.

Captured against a live run: 2026‑08‑26 Prefect server: 3.8.4, local, :4200 Code: demo/workflow-engines/
First, the question you asked

Yes — this demo starts flow runs programmatically, not from the UI. python prefect_flow.py calls tomography_scan(...) as a plain Python function. Prefect's UI can only kick off a run for a flow that has been registered as a Deployment against a work pool with a worker listening on it — this demo deliberately skips that layer, so there is nothing in the UI to click "Run" on. Section 1 below shows exactly that, straight from the server.

1How a run actually starts

The entry point is the bottom of prefect_flow.py:

if __name__ == "__main__":
    p = argparse.ArgumentParser(...)
    args = p.parse_args()
    result = tomography_scan(
        projections=args.projections, sweeps=args.sweeps,
        exposure_ms=args.exposure_ms, motor_speed=args.motor_speed,
        watchdog_s=args.watchdog_s,
    )

tomography_scan is decorated with @flow, but calling it is still just calling it — a synchronous Python function call in the same process that's running the script. Prefect intercepts that call to create a flow run, report state transitions, and attach logs/artifacts to it, but nothing about starting it required the server's UI or API to be asked first.

The alternative — the thing that would let you click "Run" in the browser — is a Deployment: a registration that says "here is this flow, packaged with a default set of parameters, and a work pool whose workers know how to execute it." This demo never creates one, on purpose (running python prefect_flow.py directly is simpler for a live demo than standing up a worker), so the server has nothing to show:

If this demo grew a "click here to scan" button, the missing piece would be prefect deploy plus prefect worker start --pool ... — genuinely more moving parts than a facility demo needs today, so it stayed out.

2The shape of one run

Every run is the same three-stage shape: arm the beamline, acquire N sweeps of projections, tear down and summarize.

prepare_beamline ──▶ run_sweep ×N ──▶ finalize (retries=2) (retries=0) (always runs, even on abort) scan_core.py orchestrator-agnostic: reuses guarded_acquire_projection from guarded_scan.py unmodified. Adds sweep splitting, a flat ScanEvent stream, and the tier-2 watchdog. rx_prefect.py the bridge — drain / log_event / ProgressTracker / sweep_table / pause_until_healthy prefect_flow.py the @flow and its three @task functions above

Every run shows up in the /runs list, colour-coded by outcome. The history below is from this session's testing: clean completions in green, one interlock abort in red, and (further down, off-screen) a couple of early CRASHED runs from debugging — more on those in Section 7.

Five things worth knowing before you read any of the three files in isolation:

1. The seam is one function call, not a rewrite

scan_core.py imports guarded_acquire_projection directly from ../synchrotron-beamline/guarded_scan.py and never touches that file. That one function is the reactive pipeline — the health gate, the five-way EPICS×Tango rx.zip, the quality flag, all of it. Everything scan_core.py adds on top (sweep_angles, to_events, sustained_low, ScanRun) exists to let an external orchestrator drive that one function N times and understand what happened — none of it changes how a projection is actually acquired. If you're trying to understand the scan itself, not the orchestration around it, that's the function to read first, and it lives in a file this project didn't create.

2. Three files, three jobs, one direction of dependency

scan_core.py    →  imports nothing Prefect-specific. Knows about rx, caproto, Tango.
                   Would be reused as-is by an n8n-facing service.

rx_prefect.py   →  imports scan_core.py's types (ScanEvent, is_healthy) and Prefect's
                   SDK. This is the only file that knows both worlds — the bridge.

prefect_flow.py →  imports both. Owns the @flow/@task decorators and the actual
                   control flow (the for-loop over sweeps, the while-loop over pauses).

Nothing flows the other way: scan_core.py has never heard of Prefect, so it's the piece that would be handed unchanged to an n8n-facing scan_service.py next.

3. Every subscription happens on RxLoop's thread — no exceptions

RxLoop() (from rx_bluesky.py, reused unmodified from the Bluesky bridge) is the very first thing tomography_scan creates. Every observable this demo builds — ring_health, sweep_frames, to_events, shutter_supervisor — is subscribed via rx_loop.subscribe(...) or rx_wait(..., rx_loop), never a bare .subscribe(). That's not a style preference: caproto and rxtango schedule their work with asyncio.ensure_future, which needs a running loop on the thread that calls .subscribe(). Get this wrong and PV reads/writes silently never fire. Section 7's Bug 2 and Section 8's findings 1–2 are both consequences of this same thread having consequences beyond just rx.

4. Two loops, two tasks per sweep, one shared counter

Read run_sweep (prefect_flow.py) as two nested loops, not one: the outer for sweep_idx, angles in enumerate(sweep_angles(...)) in tomography_scan walks the three sweeps; the inner while True: around each run_sweep(...) call exists only to handle a watchdog pause splitting one sweep into two task calls. index_offset is the thread that ties both loops together — it's the absolute projection index, updated after every single call, and it's what makes remaining = angles[index_offset - sweep_start:] (line 213) correctly resume from exactly the right angle after a pause, and what makes the HDF5 rows land in the right slot regardless of how many task calls it took to fill a sweep.

5. Read the docstrings — they're not decoration here

Every non-obvious design choice in this codebase is explained in a docstring at the point where it matters, not in a separate design doc: why to_events needs take_until(_completion_of(frames)), why drain() exists at all, why sustained_low won't fire on a flicker. If something in the code looks unnecessarily indirect, the docstring directly above it is very likely answering "why isn't this simpler" before you have to ask. (Section 8's finding 5 is the one place that trust breaks down — ScanRun's docstring claims something the diff didn't actually do.)

4The centerpiece: beam loss, a real Pause, and an automatic Resume

This is the scenario the whole thread-marshalling design in rx_prefect.py exists for. Beam loss is handled in two tiers:

  • Tier 1 is already inside the unmodified guarded_acquire_projection: each projection just waits for a healthy beam before starting. A brief dip is invisible to Prefect — only log lines.
  • Tier 2 (sustained_low) escalates a sustained drop: if beam stays down continuously for --watchdog-s seconds, the current sweep task returns early and the flow calls pause_flow_run().

The run below (spiritual-partridge, watchdog_s=3) was driven live: inject_fault.py beam_loss was fired mid-scan, the watchdog tripped a few seconds later, and inject_fault.py nominal was fired once the run showed Paused in the UI — with no other action taken, it resumed on its own.

What actually resumes it

An rx subscription is armed before the flow calls pause_flow_run(): health.pipe(filter(is_healthy), take(1)) → on the next healthy reading, call resume_flow_run(flow_run_id). That subscription lives on RxLoop's dedicated background thread, and Prefect's resume_flow_run cannot be called from that thread directly — see the gotcha in Section 7 for exactly why, and the one-line fix (pause_until_healthy hopping to a plain ThreadPoolScheduler(1) first).

5Interlock: the run that's supposed to end red

A vacuum-burst interlock is not something to pause and wait out — it aborts the scan. run_sweep raises InterlockAbort; the flow catches it just long enough to run teardown (SCAN:STATUS=ABORTED, shutter closed) and write the summary/link artifacts, then re-raises — so the flow run itself ends Failed, with the interlock as the reason, in the Prefect backend, not buried in a log line an operator has to go find.

6Quality flagging under orbit drift

Beam current and interlocks aren't the only thing gating the scan — per-frame quality is derived independently from the Tango orbit reading (|orbit_x| < ORBIT_ALARM). An orbit_drift fault doesn't pause or abort anything; it just flips every frame's quality flag, which shows up directly in the sweep table artifacts and in the summary's aggregate percentage.

7Two bugs the live stack found that the plan didn't

Both of these surfaced only once this was actually run against the docker stack, not from reading the code or the unit tests alone — worth keeping as a record of what "verified end-to-end" bought here.

Bug 1 — the scan that looked hung but wasn't

A minimal repro (bypassing Prefect entirely) acquired all four requested frames correctly, then simply never returned. to_events() merges the finite per-sweep frames stream with beam_events / interlock_events derived from health — the shared, 1 Hz ring-health poll that runs for the whole flow, not just one sweep, and never completes on its own. rx.merge only completes once every source has, so the combined stream could never signal completion, and drain() (which returns on on_completed) blocked forever — after every frame had already arrived, which is exactly what made it look like a mid-scan freeze instead of what it actually was.

Fix: to_events now applies take_until(_completion_of(frames)) — safe because a Subject-backed share() delivers a value to every observer strictly before it delivers the completion that follows it, so nothing is dropped. A regression test (test_completes_when_frames_completes_even_though_health_never_does) now pins this down with reactivex.testing.TestScheduler.

Bug 2 — the thread Prefect's SDK silently can't be called from

RxLoop runs every rx subscription on its own dedicated asyncio-loop thread. Prefect's run context — what get_run_logger() and every artifact function key off — is thread-local and doesn't cross into that thread. Worse: several Prefect calls (pause_flow_run, resume_flow_run, the artifact creators) are wrapped in @async_dispatch, which decides sync-vs-async by checking for a run context first and, failing that, falling back to asyncio.get_running_loop(). The rx loop thread always has one running — that's how AsyncIOThreadSafeScheduler dispatches — so the check wrongly concludes "async context" and returns an unawaited coroutine. Nothing raises; the call is simply a no-op.

Fix: rx_prefect.drain() only ever queue.puts on the rx loop thread; the task's own thread dequeues and invokes every callback, so logging, artifacts, and HDF5 writes all run with a valid context. The one call that can't go through drain() is resume_flow_run — it fires while the flow's thread is the one blocked inside pause_flow_run(), so there's no task thread to drain onto. pause_until_healthy hops onto a private ThreadPoolScheduler(1) first instead — a plain worker thread with no run context and no running loop, where the same check correctly falls through to the sync path. This is the same idiom rx_bluesky.RxSignal already uses to keep the rx loop free for device reads, reused here for a different reason.

Both fixes, and the four fault scenarios in Sections 4–6, were re-verified against the live docker stack after the fixes landed — the screenshots above are all from those post-fix runs.

8A closer look: six more findings from a full code review

Sections 4–6 above were re-verified against the live stack after the two bugs in Section 7 were fixed — every screenshot in this document is from a run that completed the way it was supposed to. That's a real signal, but it isn't the same claim as "the code is correct": a live run only exercises the timing that actually occurred on that run. A dedicated code review — reading every changed line against what could go wrong, not just what did — turned up six more issues, two of them the same severity class as Section 7's. Each one below was independently re-verified against the file (or, for the Prefect-internals claims, against the installed prefect package's own source) before being written up here.

1 (High) — a pause that never recovers skips teardown entirely

tomography_scan's try/except around the sweep loop only catches InterlockAbort (Section 5). But pause_flow_run(timeout=600) at line 209 is inside that same try, and Prefect's own source (prefect/flow_runs.py) shows it raises a different exception, FlowPauseTimeout("Flow run was paused and never resumed."), once its poll loop exceeds the timeout. That exception isn't an InterlockAbort, so it skips straight past the except clause. The outer finally: dispose_shutter() still runs, but everything after the whole try/except/finally block — scan_teardown, run.close(), and finalize(...) — does not. If beam genuinely never recovers within ten minutes, the flow run dies on a raw, undocumented FlowPauseTimeout: the HDF5 file is never closed, the TOMO:SCAN:STATUS PV is left at RUNNING forever, the shutter is never explicitly closed, and no summary or link artifact exists for anyone to read after the fact — the exact opposite of the audit trail this whole demo is built to provide.

Fix: catch (InterlockAbort, FlowPauseTimeout) together (both are "the scan didn't finish, report why and clean up"), or restructure so teardown runs in a finally around the whole scan body rather than only after a clean return from the try.

2 (High) — a too-fast recovery can permanently disarm auto-resume

pause_until_healthy is armed at line 204, before pause_flow_run() is called at line 209. Reading pause_flow_run's own source confirms it calls propose_state_sync(...) — a blocking round-trip to the Prefect server that actually commits the run's state to Paused — only once it starts executing, not before. So there's a real window, between arming the watchdog and that round-trip completing, where the flow run's server-side state is still Running. If beam recovers inside that window (plausible: it's right after the same 1 Hz health tick that made sustained_low fire in the first place), pause_until_healthy's take(1) fires and calls resume_flow_run — whose own source shows it raises NotPausedError("Cannot resume a run that isn't paused!") when the run isn't actually Paused yet. That exception surfaces on the private ThreadPoolScheduler(1) worker thread, with nothing there to catch it. The real failure isn't the exception itself: because take(1) already consumed its one emission before the callback ran, no second resume attempt is ever armed for this pause cycle. The flow is now stuck in pause_flow_run's poll loop — beam is fine, but nothing will resume it — until an operator clicks Resume by hand or the full 600‑second timeout elapses into finding #1 above.

Fix: catch NotPausedError in the on_next callback and retry after a short delay instead of letting take(1) spend its one shot on a premature attempt — or wait for the run's state to actually read back as Paused before treating the watchdog as armed.

3 (Medium) — a thread leaks on every watchdog pause

pause_until_healthy builds a fresh ThreadPoolScheduler(1) on every call — and every watchdog pause calls it once. ThreadPoolScheduler.__init__ owns a real concurrent.futures.ThreadPoolExecutor; nothing in pause_until_healthy ever calls .shutdown() on it, and the local pool variable that references it goes out of scope the moment the function returns. Once that executor has submitted at least one task (it has, by the time resume fires), its worker thread parks on an internal queue and does not exit on its own — only an explicit shutdown() or interpreter exit stops it. A flow with several beam-loss pauses over its lifetime accumulates one permanently-blocked OS thread per pause, for as long as the flow-run process stays up. Harmless for a short demo scan; a real concern for a long-running or frequently-interrupted production process.

Fix: reuse a single ThreadPoolScheduler for the whole flow (created once alongside RxLoop) instead of one per pause, or explicitly pool.executor.shutdown(wait=False) once the resume subscription's job is done.

4 (Low) — a spurious "beam OK" line on every sweep boundary

to_events' beam_events branch pipes health through its own fresh distinct_until_changed() — but to_events itself is called anew inside every run_sweep task, and distinct_until_changed() has no memory across separate subscriptions. The very first Health reading a fresh sweep sees always passes through, unconditionally, because there is no prior value on that subscription to compare it against — producing a beam_ok event (or, unluckily, beam_low) even when beam never actually changed state at that moment. It's exactly why every sweep's log in this document opens with "beam OK — shutter open" — which reads as reassuring, but isn't reporting a real transition; it's an artifact of resubscribing.

Fix: derive beam_events from a distinct_until_changed() pipeline built once for the whole flow (alongside the shared health stream itself), not re-created per sweep, so state is remembered across sweep boundaries.

5 (Low) — a docstring claims a refactor that never happened

ScanRun's docstring says it was "Factored out of guarded_scan.py's main()." It wasn't: guarded_scan.py was never touched by this work — its own HDF5 dtype and write logic (lines 363–373) is still there, untouched, and happens to be byte-for-byte identical to scan_core.py's independently written _DTYPE (lines 292–302). Today that's harmless — the two match. But nothing enforces that they keep matching: a future change to one HDF5 layout (a new field, a renamed column) can land in either file without anyone being told the other one needs the same change, and the two orchestrators would start writing silently incompatible schemas.

Fix: either have guarded_scan.py import ScanRun/_DTYPE from scan_core.py (making the docstring's claim true), or reword it to "mirrors" rather than "factored out of" so it stops asserting a de-duplication that isn't there.

6 (Low) — --sweeps 0 crashes with a raw traceback

sweep_angles computes divmod(num_proj, num_sweeps) with no lower-bound check. python prefect_flow.py --sweeps 0 reaches that line and raises a bare ZeroDivisionError deep inside scan_core.py, instead of a clear, actionable error at the CLI boundary where the bad input was actually given.

Fix: validate sweeps >= 1 in argparse (a type= callable, or a check right after parse_args()) so the failure points at the flag that caused it.

None of these six are fixed in the code as of this writing — this section documents what a review found, it doesn't silently patch behavior a reader might be relying on. #1 and #2 are worth prioritizing before this runs anywhere beam loss is a routine occurrence rather than a demo scenario injected on command.

9Reproducing this

  1. Start the beamline stack: cd ../synchrotron-beamline && docker compose up -d --build, then export EPICS_CA_AUTO_ADDR_LIST=NO EPICS_CA_ADDR_LIST=127.0.0.1.
  2. Start Prefect: docker compose up -d (this directory), then export PREFECT_API_URL=http://127.0.0.1:4200/api.
  3. Run a scan: python prefect_flow.py, then open http://127.0.0.1:4200.
  4. In a second terminal, try python ../synchrotron-beamline/inject_fault.py beam_loss (then nominal once the run shows Paused), orbit_drift, or vacuum_burst.

10What's next

n8n gets a genuinely different treatment, not a re-skin of this one: it has no in-process Python option at all (Pyodide is a legacy feature n8n 2 dropped), so the rx scan has to be exposed as an HTTP+SSE service and n8n's node graph becomes the visible orchestration — a Loop Over Sweeps node calling POST /scan/{id}/sweep, an IF node branching on beam health, a Wait node resumed by a fault-injection webhook. Its live feedback will be coarser than Prefect's — per-sweep node outputs, not a continuously updating progress bar — and that gap is itself one of the findings this pair of demos is for.
